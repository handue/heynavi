# voice-io

## SUMMARY
The main constraint is the build, not the voice libraries. expo-speech-recognition is the right library for always-on, on-device listening (v58.0.1 was published today; 57.x covers Expo SDK 57). It is a native module, though, so it needs a development build. On iPhone that means installing Xcode locally (the only route without a paid Apple account) or using EAS with a paid Apple Developer account. The library only wraps the legacy SFSpeechRecognizer and has no support for iOS 26's SpeechAnalyzer. It also has quirks that matter for HeyNavi:
- It does not restart itself after a session ends.
- Its default audio mode ("measurement") lowers playback volume.
- On iOS it silently falls back to network recognition, with the 1-minute and quota limits, when a locale cannot run on-device.
- Its JS on-device check only looks at the device's default locale, not ko-KR.

expo-speech (AVSpeechSynthesizer) queues utterances: stop() clears the queue and isSpeakingAsync() reports progress. It has no ducking or VoiceOver-preference options, and onError never fires on iOS. It plays the app's own speech through the speaker, the microphone picks it up, and no source shows that the library's voice-processing option cancels that audio. Plan on muting recognition results yourself while TTS is speaking, except for "stop"/"repeat" keywords; that is the dependable form of barge-in. Picovoice Porcupine is effectively out: forum posts relaying a Picovoice email say the Free Tier AccessKeys were disabled on June 30, 2026, with no non-commercial tier planned. So "Hey Navi" should be keyword matching on the continuous on-device transcript, plus tap-anywhere and VoiceOver Magic Tap as push-to-talk. Meta now has a hosted streaming STT, Muse Voice Transcribe (muse-voice-transcribe-1.0, wss://api.meta.ai/v1/asr/realtime). It supports both English and Korean with code-switching and costs $0.18 per audio hour. It has to be proxied through the FastAPI backend, and a third-party benchmark measured its P99 time to final transcript at about 1.9 s. It suits a Meta-native push-to-talk path or the Expo Go fallback, not the always-on barge-in listener. Two last facts for the fallback: Expo Go for SDK 58 is not yet in the App Store (announced as "within a few weeks"), and expo-audio's PCM stream forces the iOS "record" category, which silences playback. Together they point to SDK 57 and a half-duplex design if Xcode cannot be installed.

## RECOMMENDATION
Day 1 decision: install full Xcode today and pin one SDK, with library majors matching it. Use Expo SDK 57 + expo-speech-recognition@^57 if you want the App Store Expo Go fallback to work. SDK 58 + @^58 is fine if you only use dev builds. Then run `npx expo run:ios --device` with your Apple ID. CocoaPods will be needed for the local build.

PRIMARY ARCHITECTURE (dev build): a single VoiceController state machine in JS: LISTENING, SPEAKING (gated), SWITCHING_LANG.

1) STT setup. Call `ExpoSpeechRecognitionModule.start({ lang: 'en-US' | 'ko-KR', continuous: true, interimResults: true, requiresOnDeviceRecognition: true, addsPunctuation: false, maxAlternatives: 3, contextualStrings: [...], iosCategory: {...} })`.
- contextualStrings: Navi, Hey Navi, stop, repeat, find, read, describe, 나비, 내비, 헤이 나비, 그만, 멈춰, 다시, 찾아줘, 읽어줘.
- iosCategory: `{ category: 'playAndRecord', categoryOptions: ['defaultToSpeaker','allowBluetooth','duckOthers'], mode: 'default' }`. Avoid the default 'measurement' mode, which lowers TTS volume.
- Run a 30-minute spike comparing iosVoiceProcessingEnabled true and false on the iPhone. Keep it on only if it measurably cuts self-transcription without making TTS too quiet.
- Check on day 1 that ko-KR actually runs on-device: Korean dictation downloaded, airplane-mode test. The library silently falls back to network recognition and its JS check uses only the default locale.

2) Lifecycle.
- Auto-restart on every 'end' unless the app stopped recognition on purpose. Use backoff of 250 ms to 2 s, and restart on errors like no-speech, network and audio-capture.
- Add a watchdog for the Bluetooth bug (#133): enable volumechange at about 250 ms as a heartbeat, and if events stop while you should be listening, call abort() then start().
- Re-start on screen focus, app foreground and language change. Only one locale can run at a time, so switching language means stop and start.

3) Command layer.
- A small bilingual regex grammar runs on interim results, so stop/repeat fire within a few hundred ms. Everything else runs on final results.
- Strip an optional 'hey navi / 헤이 나비 / 나비 / 내비' prefix. Don't require a wake word inside the foreground app. Only free-form questions sent to Muse Spark need the 'Navi' prefix, which avoids false triggers from bystanders.
- Debounce identical commands for about 1.5 s.

4) TTS.
- Use expo-speech with the user's language and rate (1.0 is the system default). Pick the voice from getAvailableVoicesAsync() filtered by 'ko' or 'en'.
- Always await Speech.stop() before speaking a new high-priority message, because speak() queues.
- Keep lastUtterance for 'repeat that'. Track speaking state from onStart, onDone and onStopped; onError never fires on iOS.
- Keep a priority queue in JS (obstacle warning > object found > status) and drop stale search updates.

5) Echo gating, which is what makes barge-in work.
- While SPEAKING, and for about 400 ms after onDone, ignore every transcript except stop/repeat keywords.
- Also drop any transcript that fuzzy-matches the text currently being spoken.
- Accept a stop keyword only if it is not a word in the current utterance. Mark recognition segments that started during TTS and discard their finals.
- If false triggers persist, fall back to pausing recognition during TTS (abort on onStart, start on onDone). Barge-in then comes from the physical gestures in step 6.
- Recommend earbuds or bone-conduction headphones in the demo; they largely remove echo.

6) Push-to-talk and stop gestures that always work.
- A full-screen accessible Pressable: tap toggles listening or stops speech.
- onMagicTap on the root view does the same for VoiceOver users, and onAccessibilityEscape stops the current task.

7) VoiceOver.
- Detect it with isScreenReaderEnabled() and listen for 'screenReaderChanged'.
- Keep self-voicing through expo-speech, so stop, rate, language and gating stay under app control. Avoid live-updating accessibility labels or announcements on the camera screen so VoiceOver does not talk over the app.
- Optionally add a 'Use VoiceOver voice' setting that routes short results through announceForAccessibilityWithOptions(text, {queue: true}) and uses 'announcementFinished' for gating.

8) Camera.
- Keep CameraView in mode='picture' so it never opens the microphone, and use shutterSound: false.
- Verify there is no forced shutter sound on the demo iPhone; if there is, sample frames another way.

META STT ROLE (optional, a judging plus):
- A FastAPI WebSocket proxy to wss://api.meta.ai/v1/asr/realtime with model muse-voice-transcribe-1.0, mode ENDPOINTING, keywords ['Navi'], languageBias ['English','Korean'], key held server-side.
- Use it for push-to-talk free-form questions, where Korean/English code-switching helps. Not for always-on barge-in: P99 is about 1.9 s plus the network hop.
- Phone audio source: a half-duplex window using expo-audio useAudioStream at 24 kHz int16. Stop TTS and pause expo-speech-recognition first (#130 shows they fight over the session). Afterwards, restore playAndRecord with setCategoryIOS or setAudioModeAsync, because AudioStream sets .record, which mutes TTS.

FALLBACK IF XCODE IS IMPOSSIBLE (Expo Go, SDK 57):
- expo-speech plus expo-audio useAudioStream push-to-talk, streaming to the backend and Muse Voice Transcribe (or the file endpoint).
- Strictly half-duplex: tap or magic tap to talk, tap to stop speech, no voice barge-in.

AVOID:
- Picovoice: free tier reportedly gone, plus manual Xcode resources.
- Writing a SpeechAnalyzer native module, or routing TTS through AVAudioEngine for true AEC, in 6 days.
- Network SFSpeechRecognizer: 1-minute cap and quotas.
- Running expo-audio recording or playback concurrently with expo-speech-recognition.
- Leaving 'measurement' mode untested.
- Calling Speech.speak without stopping the queue.
- Relying on onError or speechend on iOS.
- Sending Meta keys to the app.

## RISKS
- Xcode is not installed. Without Xcode (or a paid Apple Developer account for EAS), expo-speech-recognition cannot run on the iPhone at all, so the whole always-on design depends on a local dev build working on day 1.
- Echo: on-device STT will hear the app's own TTS and any VoiceOver speech. Nothing confirms iosVoiceProcessingEnabled cancels AVSpeechSynthesizer output, and it lowers playback volume. Barge-in therefore relies on JS gating and keyword filtering, which can misfire (e.g. TTS saying 'stop').
- Korean on-device recognition may silently fall back to network if Korean dictation assets are missing. You then get the 1-minute cap, daily quotas, a Speech Recognition permission prompt and network latency, and the library gives no JS signal per locale.
- SFSpeechRecognizer recognizes one locale at a time. Mixed Korean/English utterances need a manual language switch (stop and start) or the Meta STT path.
- Continuous sessions can end or stall (issue #81, Bluetooth route changes #133 and #139, phone calls #135), so an auto-restart watchdog is mandatory.
- Audio session tug-of-war: expo-audio (#130) and AudioStream's forced .record category break recognition or mute TTS; any other library that calls setCategory can cause 'Input HW format is invalid' crashes (#84).
- Default 'measurement' mode and voice processing both reduce TTS loudness, a problem in noisy environments for blind users.
- Muse Voice Transcribe: about 1.9 s P99 time to final transcript (third-party), no client-token mechanism (needs a backend WebSocket proxy), and session caps of 60 minutes with a 10 s handshake timeout.
- Picovoice free-tier shutdown comes from forum posts relaying an email; if someone already holds a paid key the situation differs, but integration still needs manual Xcode resource steps.
- Expo SDK 58 is two weeks old and Expo Go SDK 58 may not be in the App Store yet. Mixing SDK 58 with 57-era libraries or Expo Go will fail.
- With frame sampling via takePictureAsync, a forced shutter sound (in some jurisdictions) every 1-2 s would interfere with STT and annoy the user.
- VoiceOver overlap: self-voiced TTS and VoiceOver can talk at once. VoiceOver announcements can't be cancelled by voice and are interrupted by touches.

- [M1|verified] Meta Muse Voice Transcribe exists, launched 2026-09-01 by Meta Superintelligence Labs.
- Model ID: muse-voice-transcribe-1.0. Realtime WebSocket: wss://api.meta.ai/v1/asr/realtime. File endpoint: POST https://api.meta.ai/v1/asr/transcribe (32 MB / 10 min per request).
